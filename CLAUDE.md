# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

`ram-alliance-vuelos` — the Vuelos (flights) sales system of the course project: NestJS 10 + TypeORM + PostgreSQL API in `src/modules/vuelos/`, React frontend in `frontend/`. This repository contains **only** Vuelos; the contracts of the partner teams (Alojamientos, Autos, Atracciones) live in `contracts/socios/` as the specifications our anti-corruption layer integrates against, not as code to build here. Work happens on the `vuelos` git branch.

This is phase **RDA1/RDA2**: the Vuelos API works against its own Postgres database (Aiven free in production; Neon before its compute quota ran out) and is deployed to Railway (API, auto-deploys from the `vuelos` branch) and Netlify (frontend). There is no external Payment/Customer/Billing/IdP integration yet; partner catalogs are integrated through registered providers (see `docs/planes/`). The module therefore contains its own identity service (issues the JWTs it verifies) and **simulated** payment gateway, fraud engine and mail channel behind ports.

The Vuelos module has two layers (details and route tables in `src/modules/vuelos/README.md`):

1. **Flight core (GDS)** — implements `contracts/vuelos-openapi.yaml`: search, seatmap, hold, booking, tickets, flight status. Post-sale (extra baggage, date change, cancellation + quote), check-in / boarding passes and webhooks are implemented too: **no operation of the contract answers `501`**. Their rules (fees, windows, penalties) are team decisions in `common/vuelos-config.ts` (`POSTSALE_*`, `CHECKIN_*`, `WEBHOOKS_*`), documented in `docs/planes/2026-10-07-posventa-checkin-webhooks.md`.
2. **E-commerce R1** (`src/modules/vuelos/ecommerce/`, from `docs/SRS_Plataforma_Ecommerce_LATAM.md`, release "Compra de vuelo"): identity, markets/config, search & pricing, offers/checkout, payments, orders, notifications. It lives *inside* the Vuelos module so the "enable only your module" rule holds, and sells from the core's inventory in-process.

## Agents and implementation plans

Roles are defined in `src/modules/vuelos/docs/AGENTES.md`: OpenCode/Antigravity audit and document, **Claude Code Desktop owns backend, information system and database**, Antigravity owns the full UI/UX frontend connected to the backend. Before any development work, write an implementation plan in `src/modules/vuelos/docs/planes/AAAA-MM-DD-<tema>.md` using `PLANTILLA.md` there.

## Commands

```bash
npm install
docker compose up -d       # Postgres 16 on 5432 (see the port-conflict note below)
npm run start:dev          # TypeORM synchronize:true creates/updates the schema (not in production)
npm run seed:vuelos        # flights (45-day rolling horizon), fare families, markets, places, templates; idempotent
                           # set ADMIN_EMAIL + ADMIN_PASSWORD (>=12 chars) to also create an admin; there is no default account
npm test                   # unit tests + integration tests when TEST_DATABASE_URL is set
npx jest path/to/file.spec.ts   # a single file
npm run build              # nest build (compiles specs too, so a broken spec breaks the build)
npm run migration:run:vuelos | migration:generate:vuelos | migration:check:vuelos   # schema migrations (see below)
npm run lint               # ESLint 10 + typescript-eslint (eslint.config.mjs): Vuelos, src/common, main.ts, scripts; must stay at 0 errors
npm run lint:fix           # same, applying automatic fixes (the frontend has its own `npm run lint` in frontend/)
npm run docs:modelo        # regenerates src/modules/vuelos/docs/MODELO-DE-DATOS.md from the entities (needs DATABASE_URL only to build the metadata)
npm run contract:v2:build  # regenerates contracts/vuelos-openapi-v2-ram-alliance.yaml (see "Contract v2"); contract-v2-build.spec fails if it is stale
npm run contract:events:check [-- <git-ref>]   # event JSON Schemas must stay backward compatible with that ref (default HEAD)
npm run contract:export    # regenerates contracts/vuelos-ecommerce-openapi.yaml from the running API (OPENAPI_URL)
```

On Windows the integration tests need Docker Desktop running (it stops often): `ECONNREFUSED ...:5433` means start it, then `docker start booking_db_container`. `TEST_DATABASE_URL` comes from `.env`, but the `.env` is **not** what the suites run with: `testing/integration-app.ts` clears the variables that change behaviour (`CHECKIN_*`, `WEBHOOKS_ALLOW_PRIVATE_HOSTS`, `BOOKING_*`, `GRPC_STOCK_URL`, `NODE_ID`, `PARTNER_*`) and applies only what a suite passes, because `ConfigService` reads `process.env` before the values given to the test app.

Swagger UI: `http://localhost:3000/api/docs` (Authorize with a token from `POST /api/v1/auth/login` or `/auth/invitado`). It is grouped as it was originally, with plain names and no numbering: the flight-contract sections live in `src/modules/vuelos/common/swagger-tags.ts` (Búsqueda y Catálogo, Bloqueo de Cupos (Hold), Reservas y Emisión, Postventa, Check-in y Boarding Pass, Webhooks, Estado de Vuelos) and the e-commerce controllers name their own `'E-commerce · …'` sections inline; `main.ts` builds the document with a plain `DocumentBuilder`. `src/main.ts` sets the global prefix `api` and URI versioning with default version 1, so every existing controller is `/api/v1/...` (it does **not** match the v1 contract's own `servers[].url`) and the v2 controllers (`@Controller({ version: '2' })`) are `/api/v2/vuelos/...`. The v2 contract is documented at `/api/docs-v2` (it is not part of the generated Swagger document: v2 controllers use `@ApiExcludeController()`). The server listens on `0.0.0.0` (needed for the local Tailscale integration tests). `main.ts` registers the Bearer scheme for Swagger (the only shared-file change this module needed).

`.env` needs `JWT_SECRET` (>= 32 chars). Vuelos config is validated at boot by `common/vuelos-config.ts`; an invalid value stops the app with a readable message. `DATA_ENCRYPTION_KEY` is derived from `JWT_SECRET` in development and **required** in production.

### Integration tests

`src/modules/vuelos/testing/*.integration.spec.ts` boot the real `VuelosModule` against Postgres (each suite in its own schema, dropped afterwards) and are skipped unless `TEST_DATABASE_URL` is set — point it at a disposable database such as `booking_test`, never the dev one. They cover the properties unit tests with mocks cannot: parallel bookings of one hold, inventory never oversold, idempotent replay, ownership, the purchase saga's compensation, encryption at rest. If you change booking/hold/payment logic, run them.

### Schema, migrations and deploy

`app.module.ts` synchronizes the schema only outside production, so production schemas come from TypeORM migrations in `src/modules/vuelos/migrations/` (the CLI DataSource and the entity glob live there, so new entities are picked up automatically). After changing an entity: generate a migration against a database that has the *previous* schema, then run `npm run migration:check:vuelos` against a migrated database — it must exit 0. Do not use an array-typed column `default` (TypeORM reports it as drift forever). `npm run start:render` (what Railway runs; `render.yaml` is the older Render config) does migrate → seed → start. The production database is TLS Postgres with a private CA (Aiven): set `DB_SSL_CA` (PEM) and the app, the migrations and the seed verify against it (`common/db-ssl.ts` `dbSsl`/`dbUrl`; `pg` treats `sslmode=require` in the URL as verify-full and the URL wins over the `ssl` option, so `dbUrl` strips `sslmode` when a CA is set). The Railway health check is `GET /api/v1/health/live` (no database). The backend can also run as a container on **Azure Container Apps** (`Dockerfile`, image built by `.github/workflows/container.yml` into GHCR, scripts and notes in `deploy/azure/`; the container starts with `npm run start:container` = migrate → seed in the background → API, because with a distant database the seed outlasts the startup probe; Railway keeps `start:render`; Azure for Students only allows westus/chilecentral/francecentral/spaincentral/brazilsouth): consumption plan, no Log Analytics, **max 1 replica** (jobs and stock state live in memory), `MIN_REPLICAS=0` scales to zero (while asleep no stock push, reconciliation or webhooks run), `/contracts` is copied into the image because the app reads event schemas and the v2 YAML at runtime. Never regenerate `DATA_ENCRYPTION_KEY` on a database that already holds orders. The `NormalizeSchema` migration (3NF, real foreign keys) is **one-way** and re-encrypts personal data with that key: back the database up before applying it and have `DATA_ENCRYPTION_KEY` set in production. Test a migration against data produced by the previous code, not only against an empty schema.

### Local Postgres port conflicts

If port 5432 is taken locally (e.g. a native Postgres service), create a gitignored `docker-compose.override.yml` using the YAML `!override` merge tag on `ports` (plain lists concatenate instead of replacing), and point `.env`'s `DATABASE_URL` at that port. Never edit the shared `docker-compose.yml` for a machine-local problem.

## Architecture

- **Flat module convention**: `entities/`, `dto/`, `services/`, `common/` sit directly under `src/modules/<domain>/`. Don't introduce a `domain/application/infrastructure` split. The e-commerce sub-domains (`mercados`, `identidad`, `catalogo`, `ofertas`, `pagos`, `ordenes`, `notificaciones`) are nested Nest modules aggregated by `ecommerce/ecommerce.module.ts`; the SRS naming (Spanish nouns: Oferta, Orden, Pago…) is kept for them.
- **Module wiring**: `VuelosCoreModule` (no controller) provides and exports the core services, config (`VUELOS_CONFIG`), JWT verification, the in-process `DomainEventBus` and the idempotency/inventory services. `VuelosModule` = `VuelosCoreModule` + `EcommerceModule` + `VuelosController`. E-commerce modules import `VuelosCoreModule`; never import `VuelosModule` from them (circular).
- **`src/common/`** holds only generic helpers (`IdempotencyKeyGuard` validates the header is a UUID, `ColumnNumericTransformer`, `BaseResponseDto`).
- **Money** is integer minor units in every calculation (`common/money.util.ts`, `ecommerce/common/moneda.util.ts`); strings only at the API edge. The platform sells in **USD only**: one market (`ec`); the seed deactivates any non-USD market. The market/rate model and the zero-decimal currencies stay in the code as generic utilities.
- **Errors**: always `ProblemDetailsException` → `application/problem+json`, via `VuelosProblemDetailsFilter`, attached per controller with `ProblemController(path, tag)` (never global). The contract's `code` enum is closed; codes for statuses the contract does not define live in `ExtensionProblemCode`.
- **Auth**: `auth/` verifies HS256 JWTs (`JwtAuthGuard`, `RolesGuard`, `@CurrentAuth()`); `ownerId` is only ever the verified `sub` (customer id, or `guest:<id>`). Resource access checks compare it with the stored owner.
- **Atomicity rules that must not be weakened**: `OffersService.createHoldWithin` / `BookingsService.createBookingWithin` are public so the e-commerce flow runs them *inside its own transaction*; `InventoryService` is the only writer of `Vuelo.asientosDisponibles` (conditional UPDATE); booking locks the hold row (`pessimistic_write`) and consumes it with `WHERE status='HELD'`.
- **Idempotency** (`services/idempotency.service.ts`): `execute` for single-transaction work (completion written in the same transaction), `executeSaga` for multi-step work with external effects (stores and replays the business outcome). Scoped by (key, route, owner) with a request-body hash.
- **Purchase saga** (`ecommerce/ordenes/compras.service.ts`): lock offer → revalidate price → authorise payment → order + booking + tickets + hold in ONE transaction → capture; on issuance failure void the authorisation and record a `FALLIDA_COMPENSADA` order. It is resumable by state, so a retry never charges or issues twice. Preconditions throw (not stored under the key); business outcomes (declined, compensated, success) are stored and replayed.
- **Normalized schema (3NF, real FKs)**: no arrays or jsonb for relational data (jsonb stays only for opaque documents: idempotency response, webhook payload, audit before/after). Money is `*Minor` bigint (`bigintNumber` transformer). Child tables are read through the entities' getters (`Oferta.datosPasajeros`, `FlightHold.inventory`, `Mercado.mediosPago`, `Cliente.roles`, `Vuelo.aerolinea`…), which need the children loaded: use the loaders (`hold-loader.ts`, `ecommerce/ofertas/oferta-loader.ts`, `ecommerce/mercados/mercado-loader.ts`) — they query children separately because a row lock cannot be taken on a query that joins (eager relations: pass `loadEagerRelations: false` when locking, then load them). With a join, order a paginated query by property path (`'v.fechaSalida'`), not by a quoted SQL column. `docs/MODELO-DE-DATOS.md` is generated (`npm run docs:modelo`), never edited by hand. The order copies nothing: legs come from the booking's hold items (the offer's trayectos if it never became a booking), travellers from the offer, billing identity is the shared `ecom_datos_facturacion` row.
- **Invoices** (`ecommerce/facturacion/`, admin console at `GET /admin/facturas[/{numero}]`): `FacturacionService.emitir` writes `ecom_facturas` + `ecom_factura_detalles` inside the purchase's issuance transaction (one line per leg and passenger type; IVA = the quote's tax component, subtotal + IVA = what was charged, else nothing is issued).
- **Audit trail** (`ecommerce/observabilidad/`): `auditoria_transacciones` (every domain event, ids only, unique by event id), `auditoria_sagas` + `auditoria_saga_pasos` (the purchase saga records its steps via `SagasRegistroService`; recording never fails the saga), `peticiones_http` (bounded sample written in batches, purged after `HTTP_LOG_RETENTION_DAYS`, default 7), and `auditoria_administrativa` (the admin change log, formerly `ecom_auditoria_cambios`).
- **Providers / partner integration** (`ecommerce/integracion/`): admin registers a partner service (`proveedores`: name, team, base URL — `/api/v2` is added when missing — and type) under `/admin/proveedores`: 🔄 `ping` (UP/DEGRADADO/DOWN + latency, recorded in `proveedor_salud`; also a 60 s job), 📥 `sincronizar` (imports the partner catalogue into `catalogo_externo`, what the customer sees at `/experiencias`), `PATCH {activo:false}` = kill-switch. Every call to a partner goes through `ClienteProveedor` (SSRF guard like webhooks, bounded time/size; 5xx and network errors are `ProveedorCaidoError`, 4xx are business answers), an anti-corruption `AdaptadorProveedor` (`acl/`: ATRACCIONES implemented from `contracts/socios/atracciones-openapi.yaml`; AUTOS/ALOJAMIENTOS only health, others answer 422 `PROVIDER_ACTION_NOT_SUPPORTED`) and a per-provider opossum circuit breaker (`CircuitBreakers`; only `ProveedorCaidoError` counts). `ReservasExternasService` is the reservation saga (`POST /experiencias/{id}/reservas`, Idempotency-Key): authorise payment → partner reserve (idempotency key derived from the reservation id) → confirm + invoice (one transaction) → capture, compensating (void the authorisation, cancel the partner reservation) at each failure; `Pago` and `Factura` belong to an offer/order **or** a `reservaExterna` (CHECK). `PROVEEDORES_ALLOW_PRIVATE_HOSTS` is for the course network/tests and the config refuses it in production. A provider with reservations cannot be deleted (409 `PROVIDER_IN_USE`): switch it off.
- **Idle gate** (`common/activity-gate.ts`): the periodic jobs (webhook dispatcher, holds sweeper, reconciliation, provider health, request-log purge) skip their tick when no request or event happened for `APP_IDLE_MS`, so a serverless Postgres (Neon free) can sleep; `/health*` does not count as use. Point health checks at `GET /api/v1/health/live` (no database). `DB_POOL_MAX` keeps the pool small (Aiven free allows 20 connections).
- **Event contracts** (`contracts/eventos/<type>.v<N>.schema.json`, `contracts/vuelos-eventos-asyncapi.yaml`, `common/event-schemas.ts`): every event type the code publishes has a JSON Schema for its payload (a test fails otherwise); `DomainEventBus.publish`/`despachar` validate with ajv (`EVENT_SCHEMA_MODE` strict outside production, warn in production; an invalid message from the broker is a consumer failure → retries → `q.dead_letter`). A breaking change (remove/rename a field, change a type, new required field) goes in a new `.v2` file, never in `v1`; `npm run contract:events:check [-- <git-ref>]` and CI enforce it. Docs of this stage live in `src/modules/vuelos/docs/RDA2-docs/` (microservice split, event contracts, guide mapping); the earlier audits are in `docs/RDA1-docs/`.
- **Contract v2** (Booking's template `contracts/vuelos-openapi-v2.yaml` — never edit it —, and OUR contract `contracts/vuelos-openapi-v2-ram-alliance.yaml`, GENERATED by `npm run contract:v2:build` from the template + `contracts/overlay/vuelos-v2-ram-alliance.overlay.yaml` (RFC 7386 patch) + `scripts/build-contract-v2.js`; edit the overlay or the script, never the generated file; `contract-v2-build.spec.ts` fails if it is stale or invalid, and `v2.integration.spec.ts` checks every real answer against its schemas via `testing/contract-v2-validator.ts`; docs at `/api/docs-v2`, comparison in `docs/RDA2-docs/COMPARACION-CONTRATOS-V1-V2.md`): `/api/v2/vuelos/*` lives next to `/api/v1` (global prefix `api` + URI versioning, a controller without a version is v1). `src/modules/vuelos/v2/` is a thin layer over the same services: `VuelosV2Controller` (30 operations), `OAuth2Controller` (`POST /api/v2/oauth2/token`), `BookingInboundV2Controller` (`POST /api/v2/vuelos/webhooks/booking`: Booking's CloudEvents over HTTP, authenticated by an HMAC of the raw body with `BOOKING_WEBHOOK_SECRET`, `rawBody: true` in `main.ts`), `BookingBootstrapV2Service` (registers Booking as a v2 webhook subscriber from `BOOKING_WEBHOOK_URL`/`SECRET` at boot), `PartnerAuthGuard` + `@RequiresScope` (OAuth2 `client_credentials` tokens from `POST /api/v2/oauth2/token`, clients in `vuelos_partner_clients`, owner `partner:<client>:user:<X-User-Id>`), `VuelosProblemDetailsV2Filter` (a failure declares its v2 code with `ProblemDetailsException.forV2()`), CloudEvents (`common/cloud-events.ts`; webhooks with `apiVersion` 2, feed `vuelos_outbox`), `InboundEventsV2Service` (Booking's `pagos.*`/`paquetes.*` from `q.vuelos.entrantes`), `StockPushService` (pushes `asientosDisponibles` to Booking, never writes it: **HTTP** with `BOOKING_STOCK_URL` — Booking's `POST /api/v2/inventory/stock`, one call per flight with the absolute `{service_id, item_id, date, time_slot, available_units}`, 8 at a time, sent only when Booking answers `success:true`, a refused flight waits 1 h, 5 network/5xx errors in a row stop the round — or **gRPC** with `GRPC_STOCK_URL` (`src/proto/inventory.proto`, copied to `dist/proto` by `nest-cli.json` assets); HTTP wins if both are set; `STOCK_PUSH_HORIZON_DAYS` (14) and `STOCK_PUSH_FULL_RESYNC_MINUTES` (60, gRPC keeps 10) bound the volume; `service_id` = `NODE_ID` (`NODE_VUE_RAM_ALLIANCE`); `x-api-key` = `BOOKING_STOCK_API_KEY` only when set; `flush()` is what tests use to wait for a round). Booking's production stock endpoint is on Azure and the push runs from Railway. Our contract has 32 operations (the template's 30 plus the token and Booking-event endpoints). Local integration with the other teams runs over Tailscale (our IP is the one `tailscale ip -4` prints, port 3000): `WEBHOOKS_ALLOW_PRIVATE_HOSTS=true` is needed because `100.64.0.0/10` and plain http count as private, and the config refuses it in production. v1 behaviour must not change: new optional fields are fine, new rules go behind an option (e.g. `BookingOptions.passportForInternational`). `contract-v2.integration.spec.ts` fails if an operation of the YAML is missing or does not enforce its scope.
- **Layers** (`docs/ARQUITECTURA-CAPAS.md`): `esb/` holds the internal bus — `EsbRouter` (named operations the GraphQL gateway calls, timed as `ESB <name>`), `SagaOrchestrator` (steps + LIFO compensation, recorded in `auditoria_saga_pasos`; the external-reservation saga runs on it, the flight purchase saga keeps its own code with the same step log) and `RabbitMqTransport` (only with `RABBITMQ_URL`: `DomainEventBus.publish` hands events to the broker, consumers run on delivery through `bus.despachar`, 3 retries then `q.dead_letter`; if the broker is down events are delivered in process). `gateway/` is the GraphQL BFF at `/graphql` (code-first, JWT+roles in the context, depth limit, per-request DataLoaders, graphql-ws subscriptions fed by the bus); GraphQL inputs are validated with the REST DTOs (`validarComo`), and domain errors keep their `code` in `extensions`. Logs: `common/winston-logger.ts` (files under `logs/`, gitignored; `escribirAuditoria` for the audit log).
- **Personal data** (travellers of the offer and of the GDS booking, contact, billing identity, notification bodies) is encrypted field by field with `common/cifrado.ts` via the `encryptedJson` column transformer; it cannot be queried by SQL, so lookups go through indexed plain columns (order number, PNR) and compare the surname in the application.
- **Travellers** (`entities/traveller.entity.ts`, `common/travellers.ts`): one `vuelos_travellers` row per travel document, identified by a blind index (`FieldCipher.blindIndex`: HMAC-SHA256 of `type|nationality|normalised number`, key derived by HKDF from `DATA_ENCRYPTION_KEY`), and `vuelos_passengers.travellerId`; it holds nothing readable. `ensureTravellers` upserts inside the booking transaction (`ON CONFLICT DO NOTHING`, so concurrent bookings of one person never duplicate). Documents are never searched in SQL: the admin counter hashes the query and joins on it. Changing `DATA_ENCRYPTION_KEY` invalidates the index (as it does the data). An Ecuadorian `NATIONAL_ID` (nationality EC) must be a valid cédula (`isValidEcuadorCedula`, checked after the international-passport rule); billing ids are not validated that way.
- **Counter** (`ecommerce/admin/reservas-admin.*`, `v2/admin-estado-vuelo.controller.ts`): ADMIN routes `GET /admin/reservas[/:id]` (every channel; filters pnr, partnerOrderId, paymentReference, canal, documento), `POST /admin/reservas/:id/check-in`, `GET …/cotizacion-cancelacion`, `POST …/cancelar` (Idempotency-Key) and `PATCH /admin/vuelos/:id/estado` (delay, gate; reuses `FlightOpsV2Service`). They act without being the owner through the `asAdmin` option of `BookingContextService.load` (check-in and cancellation services take it too); the events keep the booking owner so a partner hears them. Every action goes to `auditoria_administrativa`.
- **Back office** (`ecommerce/admin/`): `GET /admin/ordenes` (each passenger carries its signed `qr` and chosen seats), `/admin/ordenes/:numero`, `/admin/vuelos`, `/admin/vuelos/:id/asientos` (reserved seats with locator/order, never names), ADMIN role only; it is the single place that reads across customers. Everything else is owner-only. Test any new route for 401 anonymous / 403 guest and customer.
- **Frontend** lives in `frontend/` (its own package, excluded from the Nest build via `tsconfig.json`); see `frontend/README.md`. Brand: RAM Alliance. Do not add real card capture: payments are simulated.
- **Users and flights from the back office** (`ecommerce/admin/usuarios.*`, `vuelos-admin.service.ts`): `GET/POST /admin/usuarios`, `PUT /admin/usuarios/:id/roles` (promote/demote ADMIN; `CUSTOMER` is always kept; `409 LAST_ADMIN` for self-demotion or the last admin; roles live in the JWT so a change applies at the next sign-in) and `POST/PATCH/DELETE /admin/vuelos` (delete only a flight with no hold, booking or seat — otherwise `409 FLIGHT_IN_USE`, cancel it instead; capacity cannot drop below what is sold). Every change goes to `ecom_auditoria_cambios`.
- **OpenAPI of the whole system**: `contracts/vuelos-ecommerce-openapi.yaml` is GENERATED from the running API (`npm run contract:export`, with `OPENAPI_URL` pointing at it); never edit it by hand. `testing/contract.integration.spec.ts` fails when a route is added, removed or renamed without regenerating it. The GDS-only `contracts/vuelos-openapi.yaml` is the hand-written original and does not change.
- **Ticket QR**: each passenger's ticket has a deterministic signed code (`common/ticket-qr.ts`: `v1.<e-ticket>.<PNR>.<HMAC>`, key derived by HKDF from `JWT_SECRET`, no personal data) computed on read — no column, no migration, nothing added to the purchase transaction. The frontend renders it as a QR that opens `/verificar/<code>`, backed by the public `GET /tickets/verificar`. Changing `JWT_SECRET` invalidates the codes already issued.
- **Observability** (`ecommerce/admin/observabilidad.*`, `common/runtime-metrics.ts`): `/admin/observabilidad/resumen` is computed from the database (durable); `/runtime` reads process-local counters fed by `CorrelationInterceptor`, `VuelosProblemDetailsFilter`, `DomainEventBus`, the rate limiter and the two background jobs — they reset on every restart, so never use them as a source of truth. `GET /health` checks the database.
- **After-sale** (`services/baggage|date-change|cancellation|check-in.service.ts`, shared load/lock/ownership in `booking-context.service.ts`, pure rules in `common/postsale-rules.ts`): each write is one transaction behind an `Idempotency-Key`; a payment reference is opaque and single-use across bookings, baggage and date changes; `Vuelo.estado` CANCELLED closes a flight to search/holds/bookings. Cancelling publishes `booking.cancelled`; `PagosService` refunds through the gateway port (`REEMBOLSADO`, or `REEMBOLSO_PENDIENTE` retried by the reconciler) and `OrdenesService` follows (`DEVOLUCION_EN_CURSO` → `REEMBOLSADA`; `booking.changed` → `MODIFICADA` → `EMITIDA`).
- **Webhooks** (`services/webhooks.service.ts`, `webhook-dispatcher.service.ts`, `common/safe-http.ts`): subscriptions are per owner, the secret is encrypted and never returned; deliveries are queued by event owner and sent by a 15 s job with retries 1 m/5 m/30 m/2 h/6 h then `DEAD`; https + public IPs only (the resolved address is pinned, no redirects); `WEBHOOKS_ALLOW_PRIVATE_HOSTS` is for local tests and the config refuses it in production. Admin `POST /admin/vuelos/:id/cancelar|reprogramar` are what produce `flight.*` events. A partner's subscriptions belong to `partner:<clientId>` whatever `X-User-Id` it sends (`accountOf` in `webhooks.service.ts`), are listed/deleted from any user, and also hear events of subscriptions made earlier under `partner:<id>:user:<u>`; the dispatcher polls every 15 s by default. v2 `GET /eventos` returns `metadata.next_after` = the id of the last event (the old `evt-vue-N` form is still accepted in `after`), booking events carry `partnerOrderId`, and v2 answers 404 (v1: 403) to a booking of another user.
- **Reconciliation** (`ecommerce/ordenes/reconciliacion.service.ts`, every 60 s) is the stand-in for an outbox/broker: captures `CAPTURA_PENDIENTE` payments, voids `ANULACION_PENDIENTE` ones, re-announces issued orders with no confirmation notification. The saga records the compensated order even if the gateway cannot void. Keep every step idempotent.
- **Domain events** (`DomainEventBus`, SRS §10.3 shape) are in-process by default (RabbitMQ only with `RABBITMQ_URL`, see Layers); a failing consumer is isolated and never fails the producer. Notifications, offer expiry, the audit trail and the v2 outbox/webhooks subscribe to them. There is no transactional outbox: events are published after the commit (`vuelos_outbox` is a feed written when the event is announced, and the reconciler re-announces orders).
- **Seat selection** (optional, free in this phase): the passenger's seats (`ecom_oferta_pasajero_asientos`, one row per leg) are saved with the offer's travellers and become the GDS `assignedSeats` in the purchase saga. `OfertasService.verificarAsientos` rejects bad picks when passengers are saved and again before any charge (`SEAT_TAKEN` 409, nothing authorised); the unique index on `(vueloId, seatNumber)` is the final guarantee, and a lost race is compensated like any issuance failure. Seats are only locked when the order is issued, as the contract defines.
- **Direct flights, economy only, UTC day search** are deliberate documented simplifications — not gaps to fix silently.
